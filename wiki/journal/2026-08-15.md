## Architectural Decisions
- Preserved consumption velocity analytics as a documented specification in `plans/` rather than immediate code deployment.
- Separated pure calculation analytics (`StashVelocityCalculator`) from client network I/O.
- Removed duplication of quantity metadata (`skeins`, `total_yards`, `total_grams`) from the App Data history storage. Moving to a pack-observation model that relies on Ravelry's native `Pack` objects as the source of truth for quantity history.
- Decided against storage-level deduplication (e.g. ignoring updates with identical `pack_id`), deferring deduplication entirely to the downstream analysis/Pandas layer.

## Discoveries
- Consumption velocity is derivable from sequential `StashHistory` snapshots without requiring external database state.
- Combining trailing 30/90-day pace with total active inventory yields reliable stash lifespan estimates.
- **Ravelry API packs are history records**: Every quantity update generates a new `Pack` record linked to the primary via `primary_pack_id`. They are essentially an event log.
- **Packs lack timestamps**: Individual pack objects do not contain an `updated_at` or `created_at` timestamp. Timestamps only exist at the top-level Stash item (`updated_at`), which updates on *any* modification (even non-quantity changes like location or notes).
